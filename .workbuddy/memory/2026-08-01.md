## 第一轮：框架搭建

### 实现功能

依据需求文档完成项目骨架与全部核心模块：

**1. 项目配置层**
- `pyproject.toml`：依赖声明（langgraph/langchain/chromadb/mcp/pydantic-settings 等），dev extras 含 pytest、langgraph-cli[inmem]、ruff
- `langgraph.json`：注册三个子图入口，供 `langgraph dev` 编译为本地 REST 服务
- `.env.example` / `.env`：环境变量模板，LLM API key、外部 MCP 地址等均用占位符（`PLACEHOLDER_*`）
- `.gitignore`：排除 `.env`、`.chroma_db/`、`__pycache__/` 等

**2. 配置层（`config/`）**
- `settings.py`：`Settings(BaseSettings)` 从 .env 加载，含 LLM 路由（ollama/api）、Vault 配置、RAG 配置、外部依赖开关。`@lru_cache` 单例。派生属性 `vault_path` / `inbox_path` / `chroma_path` / `is_stub_mode`
- `prompts.py`：三个 Agent 各自独立 prompt 模板（INGESTION_SYSTEM/USER、CORRELATION_*、RETRIEVAL_QA_*），职责边界清晰

**3. 状态 Schema（`core/state.py`）**
- `KBState(TypedDict)`：按需求第6节定义全部字段
- **字段单一写入归属**：source_type/raw_content/processed_note/note_path 归 Ingestion；related_notes 归 Correlation；retrieved_chunks/answer 归 QA；messages 用 `add_messages` reducer 避免节点间互相覆盖
- `intent` 字段**移除**（需求决策：路由由 Host 选 MCP 工具完成，图内不二次判断）

**4. 核心工具层（`core/tools/`，仅内部，MCP 不暴露）**
- `llm.py`：LLM 工厂，按角色（ingest/correlation/qa）返回 ChatOllama / ChatOpenAI；`get_embeddings` 返回 embedding 模型；占位符时发 warning
- `video_to_text.py`：视频转文档占位 stub（第二轮替换为真实实现）
- `obsidian_skill.py`：笔记格式化占位 stub（第二轮改造）
- `vault_io.py`：笔记读写 + status 管理
  - `create_staged_note`：**信任闸门核心**——永远强制 `status=staged`，即使传入 promoted 也改回
  - `list_promoted_notes` / `list_staged_notes`：扫描 Vault 按 status 分类
  - `parse_frontmatter` / `get_note_status` / `read_note`
- `retriever.py`：RAG 检索器，`index_vault` 扫描 promoted 笔记分块写入 Chroma；`retrieve` 用 **metadata filter `status=promoted` 物理隔离 staged**（非阈值调节）

**5. 三 Agent 节点（`core/nodes/`）**
- `ingestion.py`：外部内容 → staged 草稿笔记，含 `_detect_source_type` 自动判别视频链接
- `correlation.py`：对已 promoted 笔记做语义检索 + LLM 输出建议关联列表（JSON）；信任闸门兜底：非 promoted 直接跳过
- `retrieval_qa_node`：仅检索 promoted 笔记回答，强制引用来源；LLM 失败时退化直出片段

**6. 三独立子图（`core/subgraphs/`）+ 图注册表（`core/graph.py`）**
- 每个子图单节点（START → node → END），对应一个 MCP 工具入口
- 模块级编译实例供 `langgraph.json` 引用
- **无图内 Supervisor**（需求决策）

**7. MCP Server 适配层（`mcp_server/server.py`）**
- 基于 FastMCP，仅暴露 3 个业务流程级工具：
  - `ingest_content(source, source_type?)`
  - `trigger_correlation(note_path)`
  - `query_kb(question)`
- **不暴露原子操作**（改 status、直接写文件、直接改双链）——信任闸门安全边界

**8. 调试入口（`scripts/debug_run.py`）**
- 第一层调试（绕开 MCP/Host）：typer CLI，子命令 ingest/correlate/query/index/status
- 直接驱动 `core/graph.py` 编译后的子图

**9. 冒烟测试（`tests/test_smoke.py`）**
- 6 项：state schema 字段、settings 占位符加载、子图编译、graph 注册表导出、vault_io status 强制、MCP 工具集与禁止工具断言

### 实现功能

**1. 视频转文本（`core/tools/video_to_text.py` 重写）**
参考 bilibili-render-pdf skill 的三级 fallback 方法论独立实现（不调用 skill 本身）：
- **第 1 级**：yt-dlp 下载平台 CC 字幕（`zh-Hans,zh-CN,zh,ai-zh,zh-Hant,en,en-US,en-GB`），转 SRT
- **第 2 级**：无 CC 时 yt-dlp 提取音频（wav）→ faster-whisper 或 openai-whisper 转写为 SRT
- 第 3 级纯视觉抽帧超 MVP 范围，未实现

**2. Obsidian CLI 适配层（`core/tools/obsidian_cli.py`，新增）**

### 发现问题与修改方法

**问题 1：MCP 2.0.0 移除了 FastMCP**
- 现象：`from mcp.server.fastmcp import FastMCP` 报 `ModuleNotFoundError`，`test_mcp_server_tool_count` 失败
- 排查：`pip show mcp` 显示版本 2.0.0；检查 site-packages，`mcp/server/` 下无 `fastmcp.py`，2.0 重构了 API
- 修改：`pyproject.toml` 把 `mcp>=1.0.0` 改为 `mcp>=1.0.0,<2.0.0`，重装后 `mcp 1.29.0`，`FastMCP` 恢复
- 教训：MCP 包 2.0 是破坏性更新，依赖需 pin 上界

**问题 2：我误把 stub 改造成"调用 Host skill"的倾向**
- 现象：第二轮我一度把 `video_to_text.py` 往"通过 MCP Client 连接外部 skill"方向写，偏离需求
- 用户纠偏："我要开发的是可以在多个类 workbuddy 平台上使用 agent，比如 codex 等。请你专心开发忽略到你本身自带的这两个功能……不要以为你本身拥有该能力就改变架构"
- 修改：完全重写 `video_to_text.py`，参考 skill 方法论但独立用 yt-dlp + whisper 实现；新增 `obsidian_cli.py` 独立封装 CLI；严格遵循需求文档第4节①流程
- 教训：**多 Host 通用是核心约束**，不能因 Host 自带能力就改变架构；可参考开源 skill 方法论但不调用 skill 本身

**问题 3：沙箱拒绝写入真实 Vault 路径**
- 现象：`debug_run.py ingest` 写 `D:/Obsidian/User Data Library/Inbox` 时被沙箱拦截（`FileNotFoundError: [WinError 2]`，随后 `SANDBOX EXECUTION REJECTED`）
- 修改：端到端验证改用临时 Vault（`VAULT_ROOT=.tmp_test_vault`），验证通过后清理
- 教训：涉及个人目录（Obsidian Vault）写入需用隔离环境验证，不触碰用户真实数据

**问题 4：faster-whisper 转写阻塞事件循环**
- 现象：`WhisperModel.transcribe` 是同步阻塞调用，直接在 async 节点里调用会阻塞事件循环
- 修改：用 `asyncio.to_thread(_whisper_transcribe, ...)` 在线程池执行，避免阻塞
- 教训：同步重计算（模型推理）在 async 上下文中必须 offload 到线程

**问题 5：Windows 控制台 GBK 编码无法输出 Unicode**
- 现象：`find ... -exec python -c "print(open(p).read())"` 报 `UnicodeEncodeError: 'gbk' codec can't encode character '\u26a0'`（⚠️ 符号）
- 修改：改用 Read 工具直接读取文件验证，绕开控制台编码问题
- 教训：Windows 环境验证笔记内容优先用 Read 工具，而非 shell print

## 架构关键决策（落地确认）

| 决策 | 落地位置 |
|---|---|
| 信任闸门：staged 物理不可检索（metadata filter，非阈值） | `retriever.py` retrieve() filter={"status":"promoted"} |
| 工具粒度：MCP 只暴露 3 个业务流程级工具 | `mcp_server/server.py` |
| 改 status 永不暴露（只能人工） | `obsidian_cli.property_set` 拒绝 + MCP 无此工具 |
| 无图内 Supervisor（Host 选工具即路由） | `core/subgraphs/` 三独立子图 |
| core/ 与触发方式解耦 | `core/graph.py` 可被 langgraph dev 直接跑 |
| status 用 frontmatter 字段不用 tag | `vault_io.py` 全程操作 frontmatter |
| 字段单一写入归属 | `core/state.py` KBState 注释 |
| **多 Host 通用**（不依赖 Host skill） | `core/tools/` 全部独立实现 |
